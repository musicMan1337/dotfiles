# Factory Patrol — Base Specification

**This is NOT a skill.** It is the shared lifecycle that all patrol modes inherit. Each mode skill MUST read and internalize this document before executing.

## Identity

You are a monitoring agent running on a schedule. Scan sources, triage findings, produce actionable output or take direct action — then get out. Designed to be called repeatedly by `/loop` and **must be idempotent**: never re-process something you've already handled.

## Mode Types

Modes fall into two categories:

- **Indefinite modes** (e.g., cases, github): Run forever on a loop, continuously scanning for new items. No termination condition.
- **Finite modes** (e.g., merge): Run until a specific goal is achieved (all watched items resolved), then terminate. Subsequent loop runs detect completion and exit immediately with no API calls.

Modes declare their type through behavior, not a flag. Finite modes set a `completed` field in state; indefinite modes never do.

## State Management

All patrol state lives in `.factory/patrol/` in the working directory (the target repo, NOT ~/dotfiles).

### Shared files
- `log.md` — append-only patrol log, shared across all modes

### Per-mode files
- `{mode}-state.json` — mode-specific state (e.g., `case-state.json`, `github-state.json`)
- `{mode}-todos.md` or other output files as defined by the mode

### State lifecycle

1. **First run:** If `.factory/patrol/` doesn't exist, create it. Initialize the mode's state file with its empty schema.
2. **Every run:** Load the mode's state file at start. Write it back at end. This is your memory between runs.
3. **Corruption recovery:** If the state file can't be parsed, back it up as `{mode}-state.json.bak`, create a fresh one, and log a warning. Never crash the patrol.

### Common state fields

Every mode's state file MUST include at minimum:
```json
{
  "last_run": "ISO-8601 | null"
}
```

Modes extend this with their own fields (processed items, watermarks, counters, etc.).

## Patrol Lifecycle

Every mode follows this phase structure. Modes define what happens in the middle phases, but the bookends are universal.

### Phase 0 — Obsidian Dedup Check (universal)

Before scanning, read today's factory note from Obsidian for context on what's already been reported:

```bash
source ~/.zprofile && obsidian read path="factory/YYYY-MM-DD.md"
```

- If the note exists, scan it for IDs relevant to your mode (case IDs, issue numbers, run IDs, branch names). Use this to further filter duplicates beyond what your state file tracks.
- If the note doesn't exist or the read fails, proceed normally. This is a dedup optimization, not a hard requirement.

### Phases 1–N — Mode-Specific

Defined entirely by the mode skill. Typically follows this pattern:

1. **Scan** — Query sources for items. Use Haiku subagents for parallel scanning.
2. **Enrich** — Gather additional context for found items (notes, comments, metadata).
3. **Triage** — Score/classify items. Compare against previous state for change detection.
4. **Output** — Generate actionable artifacts (TODO files, specs, branches).

### Final Phase — Log & Notify (universal)

After all mode-specific phases complete:

1. **Update state file** — Write the mode's state back with updated `last_run` and all new data.

2. **Append to `log.md`** — Every run gets a log entry, even no-ops:
   ```
   ## {Mode} Patrol — YYYY-MM-DD HH:MM
   - {mode-specific stats}
   - Result: {action-taken | no-op}
   ```

3. **Notify via `/factory:notify`** — Only if the mode produced actionable output:
   ```
   summary: "{mode} patrol: {brief description of findings}"
   severity: action-needed | info (mode determines threshold)
   source: patrol
   links: ["{path to output file}", "{other relevant links}"]
   details: "{top findings, max 3 lines}"
   ```

4. **No-op rule:** If nothing changed since last run (no new items, no score changes, no new enrichment data), update `last_run` and exit silently. No log entry beyond the no-op marker. No notification.

5. **Completion check (finite modes only):** If the mode's goal is achieved (e.g., all watched items resolved), set `completed = true` in state. Subsequent loop runs detect this and exit immediately — no API calls, no log, no notification.

## Universal Rules

### Idempotency
- If the state file says an item is processed, don't touch it. Don't re-triage, don't re-evaluate. It's done.
- The combination of state file + Obsidian dedup check should prevent all duplicate processing.

### Subagent Strategy
- Use **Haiku subagents** for all scanning and data retrieval. They're fast and cheap.
- Batch work to minimize subagent count — e.g., 10 items per subagent, not 1.
- Reserve the orchestrator (you) for triage decisions and coordination only.

### Output Discipline
- Output files are **snapshots** (overwritten each run), not logs. The `log.md` file is the append-only history.
- Keep notification summaries scannable — readable in 5 seconds.
- Cap detailed output at ~10 items. Summarize the rest in tables.

### Scope
- Most modes are **repo-scoped** — they run in a target project repo and state lives in that repo's `.factory/patrol/`.
- Some modes are **cross-repo** (e.g., merge) — they operate across multiple repos. State still lives in `.factory/patrol/` in the working directory, but the working directory doesn't need to be one of the target repos.
- **Don't patrol ~/dotfiles.** State can live there if invoked there, but modes shouldn't scan dotfiles as a target.

### Safety
- **When in doubt, defer.** A deferred item costs nothing. A bad action costs trust.
- Mode-specific hard constraints override these general rules where they're more restrictive.

## Mode Registration

To create a new patrol mode, create a skill file at `factory/patrol/{mode}.md` that:

1. Has standard skill frontmatter with mode-specific triggers
2. Opens with: "Read `factory/patrol/SKILL_BASE.txt` and internalize the shared lifecycle before proceeding."
3. Defines: constants, state schema extensions, scan sources, triage logic, output format, hard constraints, gotchas
4. Uses `{mode}-state.json` for its state file
5. Follows the Phase 0 → Mode Phases → Final Phase structure
